# Relay 组件级结构解析流程
- 目标：对设计稿进行组件级结构解析,将其翻译成 implement 能照着写代码的结构化组件规格。
- 输入：explore 阶段产出、写入 `delivery/<task>/context.md` 的帧映射表（帧级 nodeId 列表）+ 设计稿 `fileKey`（= context.md「UI 参数」段设计稿链接的 `id` 参数，整个任务同一个值）。**iterative 需求另传**：`迭代模式=true` + 大致宿主（取自 context.md 需求形态行）——据此做下方「迭代模式额外两件事」。
- 输出：视觉结构→nodeId 对照表（三级结构：骨架层/组件层/元素层，**按组件聚合**）+ 三张变体分表（数量①/状态②/内容③，含路径3 同组非代表帧并入的差异）+ parentmap.json（拓扑真源）+ **组件合并候选（如有，见「三、组件合并候选」——随返回上报主 agent）**。组件树由主 agent 跑 `relay-schema-gen.py tree` 从 parentmap join 对照表生成、非 subagent 手搭。
- Relay MCP 工具用法、接入、健康检查、常见陷阱 → 见 `relay-mcp.md`。

## 总则

- 所有帧由同一个 subagent 统一处理（不按帧拆分多个 subagent）
- **所有 relay MCP 工具调用必传 `designId`（= 输入的 fileKey），本文工具调用简写成 `get_design_metadata(nodeId)` 时省略了它——省的是写法不是参数**（用法真源见 `relay-mcp.md`）
- **按分组选代表帧展开**：帧映射表的"分组"列标识同页面不同状态——每组选一或多个代表帧做三级展开（选取标准详见「选代表帧」一节）；组内非代表帧不重复展开（差异在 TRD 第 4 章状态视图矩阵体现）
- 从代表帧 nodeId 向下逐层展开，产出一张完整对照表返回给主 agent
- 一份设计稿每个帧只做一次完整展开，后续复用 TRD 中的对照表
- **禁止在主 agent 中直接处理**，必须 subagent 隔离（metadata 体积大）
- **截图节制**：Frame name 明确 → 不截图，含糊（纯数字 / "组件 xxx"）→ 截图确认；**总数 ≤ 10 张、全流程共享**（选帧 / 组件层命名 / 变体 badge / 非代表帧差异比对的截图与 export_image 都算在内，非某步独享）
- **迭代模式（context.md 需求形态：iterative）额外两件事**——主 agent 在 spawn 本 subagent 时把 iterative + 大致宿主一并传入：
  1. **展开 宿主帧**：取 explore 帧映射表标 `分组=宿主帧` 那张（explore 已按「模块帧父节点」定位；若漏收，主 agent 从既有代码/设计稿补定位，仍缺则向用户索取——**不得用新模块单帧顶替、不得猜楼层顺序/间距**，完整约束见 `exit-rules.md`「迭代协议衔接举证」）。展开它量出新模块与相邻既有楼层的**楼层顺序 + 间距/对齐/层叠/共享背景**，供 TRD §4「衔接约束」；既有楼层**只测不建对照表行**（既有代码、不重写）。该帧同时设为 workflow-visual-check 的 `pageNodeId`。
  2. **对照表加 host/sibling 锚点行**：在对照表顶部标一行 `[host]`（宿主容器 nodeId）+ `[sibling]`（相邻既有兄弟 nodeId），`reuse` 列写「既有·只读」——供 `tree` 生成时把新组件挂到宿主锚点下、implement 骨架据此 root 到 host 帧。**不展开既有兄弟内部**（避免圈进既有代码）。**宿主帧的 raw 必须并入 `parentmap` 生成**（`relay-schema-gen.py parentmap --raw` 可重复传多帧合并）——否则 host/sibling 的父子拓扑不在 parentmap 里，`tree` join 时新组件找不到宿主祖先、会平铺挂到 Page 下，「挂到宿主锚点下」落空。
  greenfield 模式无此两件事。

## 一、组件拆分

### 选代表帧

**先选代表帧**：

1. 按帧映射表"分组"列聚合
2. 每组选代表帧——选取标准：
   - **默认选一个**：优先选 children 数量最多的（结构最完整），次选帧名语义最明确的
   - **组内结构差异大时可选多个**：帧名语义明显对应不同功能流程（如"待支付"/"已支付"/"查询失败"属不同业务状态，结构必然不同），或帧名后缀差异暗示独有内容（如"-带重试""-含广告"）——此类帧也选为代表帧，确保对照表覆盖所有独有结构
   - 若难以判断，截图对比后选内容最丰富的
3. **置信度处理**（展开前检查代表帧的置信度）：
   - 高：直接展开
   - 中：展开时须截图确认帧内容识别是否正确
   - 兜底：展开前返回给主 agent，由主 agent 向用户确认该帧含义后再继续

**再逐帧展开**：对选出的每个代表帧的 nodeId 调用 `get_design_metadata(nodeId)`，获取完整子节点树；非代表帧不展开。

> 优先 `maxDepth=3`，不足再完整拉取。目标是拿到 2-3 层嵌套结构。

### 识别骨架层

骨架层是页面的容器骨架——把「整页怎么分块布局、背景谁来渲染、组件挂在哪个容器」定下来；它可多层嵌套，故从帧向下**逐层**识别这些**布局容器**（不限帧的直接子节点，帧与骨架之间也可能夹透明包裹层）：

**判定标准**（满足全部）：
- 自身带视觉属性（背景色/渐变/圆角/分区边界）
- 不承载业务逻辑（无交互、无数据绑定语义）
- 包含多个子节点（是其他组件的包裹容器）

**典型信号**：Frame name 常含"背景/容器/区域/section/wrapper"，面积占帧较大比例。

**排除**：帧本身不算骨架层（帧是输入锚点，不进对照表）。

### 识别组件层

在骨架层容器内部（或直接挂在帧下方的非容器节点），识别**业务组件**：

**判定标准**（满足任一即可——组件是主产物，判据放宽宁纳勿漏；骨架/元素从严）：
- 承载独立业务职责（导航栏、订单卡片、商品列表项、按钮组等）
- 有交互语义（可点击、可滑动、有状态切换）

**与骨架层的边界**：一个节点同时命中骨架与组件判据（如自带背景色的业务卡片）时归**组件**；其背景/圆角/内边距在备注记明，由 wrapper 或组件自身承接，别让视觉随归类丢失（否则下游出口会触发「带视觉容器无渲染 owner」告警）。

**命名优先级**：
1. Frame name 有明确语义 → 直接采用
2. Frame name 含糊 → 截图识别（`get_screenshot`）确认用途

**nodeId 取「最小包围子树」**：记**刚好框住该组件**的容器根，别圈进宿主 chrome（状态栏/导航）、他楼层（推荐流/搜索框）或整页背景；全页态（如异常兜底页）记**内容卡片子树**而非页面根帧。自检：子树里混进上述非本组件的兄弟，即锚点取大，向下收到组件自身容器根。
> 为什么：此 nodeId 是下游 implement 阶段 `get_node_data` 的入口，圈松一点，成本沿 `get_node_data → normalize → 静态稿 → 改写` **逐级放大**——多圈的宿主 chrome/他楼层内容会一路被生成再删除。

**⚠ 合成组件（无单一容器）—— 检出即上报，禁止自选 root**：一个业务分组的成员是**大容器（页面帧/大骨架）的直接兄弟、没有任何单一节点恰好框住它们**（要么只能取整帧=圈进他组件、要么取某个成员=漏掉其余）——如 header/banner/散落 badge。此时**不成立「组件=一棵最小包围子树」**，是**设计稿数据质量缺陷**（本应把成员合并进一个 frame）。
- **禁止**：随手挑一个成员当 rootNodeId + 写备注糊弄——这是**静默收敛**（下游 `get_node_data(该成员)` 会漏捞其余成员，见 `design-rule.md`）。
- **须做**：把它当**低置信项上报主 agent**（同「置信度兜底」通道）——返回 `{组件名, 成员 nodeId 列表, 共同祖先=帧}` 并标「合成组件·无容器」，由主 agent 向用户暴露、走签收（两路[改稿合并 / 占位]见 `schema.yaml` §2「合成组件处置」）。**不要在对照表里塞一个假的合成 root 行**——成员照常各自作对照表行（真实 nodeId），保持 nodeId 全合法、verify/tree 不受影响。

### 识别元素层

在组件层内部，识别**独立的视觉元素**：

**判定标准**（满足全部）：
- 用户可感知的独立视觉单元
- 样式上具有独立特征（特殊颜色、特殊字号、独立 icon、独立图片/标签）
- 样式不完全由父组件继承决定

**典型条目**：
- 标题文案（特殊字号/字色/字重，含艺术字/特殊字形标题）
- 价格/金额（红色/特殊字号）
- 图标组（独立的 icon 集合）
- 标签/badge（独立背景色+文字）
- 楼层标题图（image 类）
- 状态图标（不同状态不同图）
- 券形锯齿 / 虚线分隔 / 票根缺口

**收敛规则（留表门槛，防对照表被纯锚点噪音淹没）**：一个视觉元素命中上面判定标准后，还须**服务至少一个下游消费方**才单独成行——否则折进父节点备注、不逐一列：
- **数据绑定**：将进 §2.4 数据绑定表（消费某接口字段）
- **实现坑点**：备注需记非显然约束（如幻影副标题合并、绕排、scope-excluded、条件显示）
- **变体 targetId**：是 §2.2 三张分表某行的 `改哪个元素`/元素锚
- **需切图导出**：位图/艺术字/券形锯齿等 implement 要 `export_image` 的元素（nodeId 是导出锚）
- **有交互 affordance**：将进 §4.2 交互清单表（可点/可滑/可输入）

五类都不沾的纯装饰/纯布局文本（普通段落、无特殊样式列表项、继承样式的容器内文字）**不单独成行**——它们无 nodeId 消费方，列出只增审核负担。

## 二、多状态覆盖

### 组件状态变体识别

代表帧对照表完成后，对其中的**列表类 / 卡片类组件**，识别该组件的**状态变体节点**（设计师用于展示同一组件在不同业务状态下视觉差异的参考图）。

**跳过条件**（先判要不要做本节）：代表帧内无列表/卡片类重复组件；且帧外无同源散落节点（路径 1 无）；且帧映射表中无匹配路径 2 的组件级帧；且同组无非代表帧（路径 3 无）——全不命中则本节整节跳过。

变体节点有三种来源。**diff 的基线(右)恒为「代表帧里的该组件」**（§1 已展开的默认态）；三路只是**变体源(左)的形态**不同（先看下表把握结构，逐条判据见后）：

| 路径 | 变体源在哪 | 变体源 = diff 左 | 基线 = diff 右 |
|---|---|---|---|
| 1 | 帧映射表**外**（画布散落） | 散落的**一整份**变体组件 | 代表帧里的同源组件 |
| 2 | 帧映射表**内**（组件级小帧） | 该小帧（**整帧 ≈ 一份**变体组件） | 代表帧里的同源组件 |
| 3 | 帧映射表**内**（页面级同组帧） | 非代表帧里**嵌着**的该组件（先定位再比） | 代表帧里的同源组件 |

满足对应路径任一即纳入：

**路径 1（帧映射表外 · 散落节点）**，同时满足：
1. 与代表帧内的某个 instance/frame 共享相同 name（如 `优惠券`、`营销型优惠券`）
2. DOM 骨架匹配度 ≥ 80%（子节点 name 序列一致）
3. 位置特征：x 与基准帧对齐，y 在基准帧下方（间距 ≤ 帧高度 × 3）
4. 不属于帧映射表中任何已识别的帧

**路径 2（帧映射表内 · 组件级帧）**，同时满足：
1. 属于帧映射表中的某个帧（已有 nodeId）
2. 帧尺寸明显小于页面帧（宽度 < 页面帧宽度的 80%），或帧映射表中的分组名/状态名含「状态」「变体」「组件」等组件级信号
3. 与代表帧内的某个 instance/frame 可建立同源关系（共享 name 或 DOM 骨架匹配度 ≥ 80%）

> 路径 2 解决的问题：explore 阶段帧映射表会把组件级变体节点（如券卡片的 4 种状态）识别为独立帧，若此处仅按路径 1 的第 4 条排除「已在帧映射表中的节点」，这些变体就会被跳过。

**路径 3（帧映射表内 · 页面级同组非代表帧）**：同组内未被选为代表帧的整页帧（在帧映射表中、§1 选帧时未选中），变体藏在帧内某组件，轻量扫描发现：
1. 对非代表帧调 `get_design_metadata(nodeId)`，与代表帧对照表比对
2. 找出**独有元素**或**同名元素但视觉/内容不同**的节点
3. 组内只有一个帧、或差异仅文案/数据取值（不涉及结构/样式/状态）→ 无路径 3 变体

> 三条路径都只是**发现通道**，发现的差异统一走下面「变体三层建模」按三层归位（状态→②/内容→③；**纯样式微调**、够不上独立状态的 → 记该组件对照表备注、不进三分表），最终汇入同一套三分表——单一落点，避免同一状态在两处各记一遍（决策散落）。三通道发现的变体帧全部计入下游「变体完整性自检」的分母。

### 变体三层建模

#### 三层模型 + 信号归类

找到变体源后与代表帧基线做 DOM diff，每条差异按**判定顺序**归入三层之一：先问「**数量**驱动吗」→①；否则「**业务状态**驱动吗」→②；否则「**数据种类**驱动吗」→③。三者可叠加（如券卡 ②状态+③面额），但**分别建模、不建组合树**（不为 `数量×状态×内容` 建 N×M×K 棵表）。

| 层 | 触发信号（DOM diff 命中即归此层） | 落表 | implement 消费 |
|---|---|---|---|
| **① 数量→布局** | instance 计数变化；或子帧总宽溢出容器（`lastChild.x+width > container.width`） | 数量布局表 | 算 `list.length` 选 branch，**非** patch |
| **② 状态→生命周期** | 按钮/操作区 TEXT 文案成有限枚举；或角标/覆盖层显隐（pos=(0,0) 的 ellipse+text 子节点） | 状态变体表 | 条件渲染；delta 作用域**限本组件** |
| **③ 内容→渲染** | 同元素按数据种类换分段/富文本（折扣 vs 满减）；或状态装饰图/角标图不同（含装饰曲线的切图按状态复用，非独立状态行） | 内容渲染表 | 数据驱动分支，**非**状态、**非**新增切图决策 |
| **（边界，不进三分表）** | 极值文案：长度异常/数值溢出（如"满20000000"） | → 进 §6 边界 | — |

> 环境驱动的 ④主题 / ⑤视口（暗黑/响应式）**走 CSS、不进三分表、仅 PRD 明确要求才登记**（H5 等比 px→vw 不算），故本步不产它们。

#### 层① 数量布局采集细则

数量布局表怎么采（适用于同分组有多个基准帧、内部同名 instance 数量不同时）：
- **按布局差异逐档枚举 case**：布局（尺寸/排布/是否横滑）不同的数量档各成一行、按计数递增排列；布局完全相同的相邻档才可合并区间。**必须记录各档的 item 尺寸(宽×高)与内部结构差异**（文案行数/按钮尺寸/布局变化），不能只记「数量=N」。（券楼层恰是 1/2/≥3 三档各不同：铺满 / 并排 / 横滑——档数按组件实际布局定，非固定三档。）
- **溢出/横滑**：末卡右缘超容器（`lastChild.x + lastChild.width > container.width`，即差异表「子帧总宽溢出容器」信号）→ 该 case 记 `overflow: scroll-x`，并算 peek 比例 = `(containerWidth - lastFullyVisibleChild.right) / nextChild.width`。
- 采集结果落**数量布局表**对应列（`case / presentation / item尺寸 / overflow / peek`）。

**分表填写规范**：
- **`rootNodeId`（首列，机器抽取键）**：该行所属组件的根 nodeId，**必须与该组件在「对照表」heading `### 组件：<name> (rootNodeId: X)` 的值一致**（同源）。层③按元素聚合，其 `rootNodeId` = 该元素**所属组件**的根（直接锚定 owner，下游 implement 据此把三层行装配成 per-component 投影，免按名/父链反查）。
- 层①数量布局：case/overflow/peek 采法见上「层① 数量布局采集细则」；`item尺寸` 作 presentation 判别信号可保留（区别于元素对照表的样式值）。
- 层②状态：`改哪个元素` 记 targetId + `改什么` 的定性；badge 记 **nodeId 锚点**，不抄色值（值由 implement 取）。
- 层③内容：只记 `数据种类 → 分段结构`；具体字号由 `normalize` 的 `text_segments` 取，不抄。
- badge-image（一张切图按状态/数据种类复用）归**层③**，不混进层②状态行。

### 变体完整性自检（出口强制 = 闸门零种子）

三张分表产完后，**强制**对账「设计稿实有变体帧 vs 分表覆盖」，缺则**阻断出口、回去补**：

- **分母**（设计稿实有变体帧）= 帧映射表（context.md，已落盘）按分组列出的状态/数量/边界帧 **∪** 本节「组件状态变体识别」路径 1/2/3 枚举出的变体帧。**`分组=宿主帧` 的行不计入分母**——它是迭代衔接真源、非本组件变体（详见「迭代模式额外两件事」），计进来会误报缺变体。
- **分子** = 三张分表覆盖的 case（层①）/ 态（层②）/ 数据种类（层③）所引的代表帧。
- **报缺** = 分母有帧、分子无对应行 → 列出「设计稿存在但分表未覆盖的变体帧」，**阻断出口**。
- **机器 vs 判断**：集合差集（分母帧 − 分子行引帧）机械算出候选缺项；由本 subagent 判差集里的帧是否真是本组件独立变体（排除他楼层/宿主 chrome 误配），确认真缺才阻断。
- **MCP 断连降级**：只用已落盘帧映射表做**帧存在性**检查（「设计稿有第 3 档帧、分表无此行」这类仍拦得住），帧内部精确差异待重连再补——**不因断连放行为「已覆盖」**。

> 本自检只查「分表**覆盖全了没**」（相对设计稿实有帧的完整性），**不查**分表内部三层拆得对不对——后者是「变体三层建模」的职责。④主题/⑤视口无需求、无帧，**不在本自检对账范围**（否则会误报「没做暗黑态」这种根本没要求的项）。

## 三、组件合并候选

在已识别的组件之上做一次**跨组件**观察（非第四层，是关系分析）：同一容器下的多个兄弟组件，若**槽位骨架同构**（同一套子槽位，如「左图 ｜ 中文 ｜ 右状态列」）、仅内容/状态不同 → 作为**「组件合并候选」随返回上报主 agent**，返回 `{候选组件名列表, 共同容器, 同构依据, 档位}`（是本流程「输出」段声明的产出之一）。分档标置信度：

- **同 `componentSet`**（设计已声明为一个组件的变体）→ 高置信。
- **不同 componentId 但槽位同构 + 关键列对齐**（如各行右状态列同一左边界 x；**读 rect.x 判对齐即可——坐标只用于判断、不写进对照表，与备注列「禁抄坐标」不冲突**）→ 中置信。
- **骨架不同构**（子槽位数量/角色/顺序明显不同）→ 不上报。

**只检测 + 上报、不在对照表合并**：一组件 = 一棵最小包围子树，两个兄弟是两棵子树，强并会触发「合成组件·散落」告警。是否合并成一个组件、如何统一逻辑，由主 agent + 用户在 `schema.yaml` design 章「组件合并候选处置」定。

## 四、结构化输出

### 对照表（视觉结构→nodeId，按组件聚合，不按帧平铺）

**按组件聚合输出**，不再「每个代表帧一张独立表」——组件是唯一结构单元，对照表挂在组件下而非帧下（拓扑真源是 parentmap，组件树是其派生视图）：

- **全帧共有的组件**（如 HeaderBanner）：出**一份**组件条目表 + 一张「跨状态差异」小表（各态 nodeId + 简述），**不在每帧里重复整块**（避免五元素抄 4 遍）。
- **状态独有的组件**（如 EmptyState / ErrorFallback）：在其所属状态下记**一次**。
- 多代表帧的组件：同一份表内标注各条目所属帧。

```markdown
### 组件：HeaderBanner (rootNodeId: `10:13287`)

| 层级 | 名称 | nodeId | reuse | 备注(定性，不抄值) |
|------|------|--------|-------|------|
| 骨架层 | 顶部背景区 | 10:234 | | 线性渐变（色值 implement 取） |
| 元素层 | 楼层标题图 | 10:300 | | 艺术字+渐变（定性描述） |

#### HeaderBanner 跨状态差异
| 态 | 差异元素 | nodeId | 简述 |
|----|----------|--------|------|
| 已领取 | 标题文案 | 10:302 | "已领，去使用" |
```

**备注列规则（锚点不抄值）**：
- 只记 **nodeId 锚点 + 定性描述**（「线性渐变 / 票券形态 / 位图 / 艺术字」）。
- **禁止抄具体色值/尺寸/坐标**（如 `#FFE8F0→#FFF`、`375×47`、`¥80 大红字`）——精确值有确定源头（设计稿 nodeId），由 implement 的 `normalize`/`export_image` 取，抄了就是漂移源。

对照表**只贴语义**（nodeId + 名称/层级/reuse/备注），父子拓扑由 `parentmap.json`（机器版，唯一拓扑真源）提供、组件树由脚本 join 生成（见下方「组件树」段）。你只需保证每个 nodeId 真实、准确——它是 join 的锚。

**reuse 列**：subagent 不判定 reuse，该列统一留空。reuse 识别由主 agent 在收到对照表后，结合 codegraph/node_modules/公共组件知识库完成。


### 组件拓扑parentmap

组件树的父子拓扑**全部来自机器版 parentmap**——它是**唯一拓扑真源**：既喂 `tree` 生成组件树、又喂 `verify-tree.py` 校验对照表 nodeId 合法性与「带视觉容器」owner 归属。产出：

1. 对**对照表涉及的每个代表帧**调 `get_node_data(designId, 帧 nodeId, includeChildrenData=true)`（合起来即**整页级**覆盖；缺帧会让那些 nodeId 落进 tree/verify 盲区）——返回体大，MCP 自动落盘，记下各落盘路径（比 metadata 重，但仅本步用、且不进上下文）。
2. 跑 `python3 .workflow/node/workflow-implement/relay-schema-gen.py parentmap --raw <帧1落盘> --raw <帧2落盘> ... --out delivery/<task>/schema/parentmap.json` 合并出整页扁平映射 `{nodeId:{parent,name,type,hasVisual}}`。
3. 该文件是 `schema-draft` 角色产物，是下游 `tree` 生成与 `verify-tree` 校验（nodeId 合法性 + 带视觉容器 owner）的输入，不写进 TRD 正文。

> **产物归属**：对照表 + 三张变体分表 + 自检结论随返回**上报主 agent、不自行落盘**；唯 parentmap.json 由 subagent 自行落盘（上）。**组件树不在返回物**——主 agent 把对照表写入 `delivery/<task>/schema/component-table.md`（机读，不进 design.md 正文；§2.1 只留指针）后跑 `tree` 生成、写进 design.md §2.0。

### 组件树（由脚本生成，subagent 不手搭）
由 `relay-schema-gen.py tree` 从 **parentmap(拓扑真源) + 对照表(语义，`delivery/<task>/schema/component-table.md`)** join 生成，拓扑正确 by construction（兄弟不会被写成父子，根除 #6 类错嵌）。subagent 只管产出**准确的对照表 + parentmap**；生成动作在主 agent 侧（见 `schema.yaml` §2）。

生成后的形态（脚本按此渲染，供参考）：

```
Page
├── 骨架层A (骨架容器)
│   ├── 组件层B (业务组件)
│   │   ├── 元素层C
│   │   └── 元素层D
│   └── 组件层E (业务组件)
└── 骨架层F (骨架容器)
```

**脚本的渲染规则**：根 = Page；每节点的树父 = parentmap 沿 parent 链**最近的、也在对照表里的祖先**（中间未列入对照表的容器自动折叠）；类型标签 骨架层→`(骨架容器)`、其余→`(业务组件)`；节点集与顺序来自对照表。
