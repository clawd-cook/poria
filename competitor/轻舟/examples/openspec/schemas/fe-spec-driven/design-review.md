# design.md 内容审核流程

> fe-spec-driven schema 专用。propose 定稿前 subagent 隔离执行。
>
> 输入：完整 design.md 内容 + PRD 前端功能点摘要（逐项列出的功能点清单，一行一条，由主 agent 从 PRD 提取后传入）。
> 输出：结构化审核报告（问题清单 + 结论）。

## 总则

- 审核视角 = **implement 阶段的开发者**：拿到这份 TRD 能否直接写代码？会不会撞墙？
- 只报告 implement 会遇到的问题，不评价方案设计的优劣
- 每个问题必须给出具体位置（章节/行号/条目名）和修复建议
- 审核不修改 design.md，只产出报告返回给主 agent
- **与 exit-rules 的分工**：exit-rules 负责可机械验证的格式/结构规则（标题存在、表格列齐、nodeId 格式合规、字段路径子串匹配等）。本审核只做 exit-rules 验不了的**语义层判断**——不重复检查格式问题

## 审核维度

### 维度 1：implement 可执行性

检查对照表与状态矩阵的语义合理性：

- 渲染方式是否与上下文语义一致：
  - `image` 行的备注是否暗示其实是接口返回的动态 URL（→ 应为 `component` + 数据绑定表）
  - `component` 行如果标记了 reuse，组件协议是否找到了（未就绪组件仍在实现计划中 → 🔴）
- 参数取值是否明确：
  - 组件的枚举型/配置型 props（如 mode、type、variant、maxCount）以及接口入参中影响返回结果的筛选参数（如 bizType、channel），须在对照表备注或数据绑定表中给出具体取值
  - 判定标准：该值非运行时动态决定（非用户输入/非接口返回），却未在 design.md 中写明 → 🔴
- 第 4 章状态矩阵语义检查：
  - 非代表帧独有元素是否在矩阵中有对应行（标注为"独有"+ nodeId）
  - "样式变化"与"文案变化/数据变化"是否分类正确（如实际是换了 icon 但标成了"数据变化"）

### 维度 2：歧义检测

扫描全文，找出可被两种方式理解的描述：

- 同一内容在不同章节的描述是否矛盾
- 渲染方式与备注/上下文矛盾（具体 image/URL 判定见维度 1，此处关注其他类型矛盾）
- 状态名在帧映射表和状态矩阵中是否用了不同名称指代同一状态
- 接口字段与数据绑定表中的字段路径语义是否匹配（如绑定表写 `order.price` 但接口出参实际嵌套在 `data.orderInfo.price`）

### 维度 3：交叉一致性

产物之间的对应关系：

- **对照表 → 状态矩阵**：对照表中的组件层/元素层条目全部出现在矩阵横轴（骨架层通常不在矩阵，有变化时除外）
- **数据绑定表 → 对照表**（反向确定性检查）：数据绑定表中的每个条目须能在对照表中找到对应的组件/元素
- **帧映射表 → 状态矩阵**：帧映射表中的所有状态全部出现在矩阵纵轴
- **组件树 → 第 6 章**：组件树中有交互的组件（判定：对照表备注含点击/提交/切换/滑动等动词，或状态矩阵中该组件有状态变化），在异常流中有对应覆盖

### 维度 4：遗漏检测

将 PRD 前端功能点逐一对照 TRD：

- 每个功能点是否在对照表+状态矩阵中有实现路径
- 帧映射表中是否有对应状态覆盖
- 接口列表是否覆盖该功能点的数据需求
- 有设计稿的功能是否有 nodeId 可供 implement 拉取样式

**豁免**：纯逻辑行为（跳转/调用/缓存更新等无 UI 呈现的功能点）不要求在对照表+矩阵中出现，但须在第 3 章状态机或第 6 章异常流中有覆盖。

## 输出格式

```markdown
## design.md 审核报告

### 审核结论：✅ 通过 / ⚠️ 有问题需修复

### 统计

| 🔴 阻断 | 🟡 警告 |
|----------|---------|
| N 项 | M 项 |

### 问题清单（按严重度排序）

| # | 严重度 | 维度 | 位置 | 问题描述 | 建议修复 |
|---|--------|------|------|----------|----------|
| 1 | 🔴 | implement 可执行性 | 第2章 xxx行 | ... | ... |
| 2 | 🟡 | 歧义检测 | 第4章 xxx条目 | ... | ... |

### 各维度概况

- 维度 1：<一句话结论>
- 维度 2：<一句话结论>
- ...
```

**严重度判定**：
- 🔴 **阻断**：implement 必定撞墙——渲染方式与语义矛盾、未就绪组件仍在计划中、样式变化缺 nodeId、PRD 功能完全无覆盖
- 🟡 **警告**：implement 可能需要额外调工具或向用户确认——信息不够精确但不缺失、交叉引用有偏差但可推断、变化类型分类可商榷

**审核结论判定**：
- 有 🔴 项 → `⚠️ 有问题需修复`
- 仅 🟡 或无问题 → `✅ 通过`

## 落盘

subagent 将审核报告返回给主 agent（不自行落盘）。主 agent 负责：
- 🔴 项：修复后回到 exit-rules 步骤 2 重验（含格式校验 + 重新审核）
- 🟡 项 + 报告：展示给用户确认

## 禁止项

- ❌ 修改 design.md（审核只读）
- ❌ 评价方案设计优劣（"建议用 XX 方案替代"——不是审核职责）
- ❌ 对照表逐行复述无问题的条目（只报问题，各维度概况一句话即可）
- ❌ 跳过任何审核维度
- ❌ 将 🟡 虚报为 🔴（阻断项标准严格：必须是 implement 一定会撞墙的）
- ❌ 重复检查 exit-rules 已验过的格式/结构规则（nodeId 格式、标题存在、表格列齐等）
