# workflow-explore：需求探索（工作流起步节点）

本节点是 feature 类 profile 的**起步/触发节点**（profile 的 `start_node`）：跑 `/workflow-engine init` **之前**的第一步，专做需求澄清。它**在状态机之外**——这是分阶段加载的有意设计，不是例外：

- **起步只加载澄清需求所需的**：`docs/spec-rule/design-rule.md`（规约必守 + 经验/踩坑段扫一遍）+ 相关 `module-/tech-knowledge` + 用户带来的 PRD（文件路径或正文）。
- **刻意不加载工作流编排细节**（PROTOCOL / profile / 状态机机制）：既省上下文 token，又让发散思考不被流程纪律压着。编排细节在探索谈清、人手动 `init` 之后才加载。

结论靠**同会话上下文**传给下游，不落文件。

## Schema 增强（按项目类型加载）

检查 `openspec/config.yaml` 是否存在且指定了 schema：
- 有 → 读对应 schema 的 `explore` 段（如 `openspec/schemas/<schema>/schema.yaml` 中的 `explore.instruction`），作为本次探索的额外能力和视角补充
- 没有 / schema 无 explore 段 → 跳过，正常探索

这不改变 explore 的自由度——schema 只补充信息源和校验视角，不限制探索方向。

## 深度探索

进入即**复用skill `/openspec-explore` 并完整继承其 stance**：深入想、自由画图、跟着对话走到哪算哪——没有固定步骤、没有规定产出、不赶时间。该挑战的假设挑战、该画的状态图/对比表/依赖图照画、该追的线索追到底。**探索是否充分由问题本身的清晰度决定，不由「该开始执行了」决定。**

- 别为了喂下游而提前收敛：宁可多开几条线程让用户挑，也不要 funnel 成单一问答把需求草草定型。
- 后段（implement→...）机械化的前提，是这里把边界/约束/未知/风险假设想透了。这里提前草草收尾，后面返工成本非常昂贵。
- 这里上下文干净、没有状态机的流程纪律压着你——正是发散的最佳时机。别急着进 init。

如果找不到 `openspec-explore` 直接退出，提示用户。

## 出口

**悬问闸（MUST）**：本轮回复里只要向用户抛出了尚未得到回答的问题，**禁止**在同一条回复里给下面的 init 提示，因为过早的下一步提示会干扰用户对需求完整度的判断。

所有问题都有结论后，在给 init 提示前：
1. **权限判断** 如果当前需求涉及多仓库改动，需要进行权限盘点，如果缺少改动权限请发起授权，不能因为权限问题缩减需求。
2. **打印关键决策清单**：通读整段探索，结构化输出用户拍板的关键决策——**读 `decision-list.md`**（判据「记什么」+ 结构示意都在里面）。
3. **确认闸（`AskUserQuestion`）** 打印清单之后向用户确认结论，如果用户有修改，回显增量即可、再确认一次。确认无误才放行——期间改过就在放行前把定稿完整列一次做锚点，没改过直接放行不重印（why：多版本清单会让 propose 读错终版）。

> 准备好就跑 `/workflow-engine init <task>` 开始任务。
