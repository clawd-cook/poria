这份地图干嘛用？让 test-plan 决策物料时**照图索骥**：这个域有哪些料、各服务什么场景、哪些自助哪些摊牌——省掉每任务重新探"要什么料、从哪搞"。

## 什么料该上图 = 需要 setup × 复发频率

扣住这两条，别的别乱加：

- **需要 setup（主轴）**：拿到这条料要不要**启动额外进程、配置外部服务、准备特定账号/权限**才能把依赖摆到目标状态？要，才上图。一行代码能注入的（props / localStorage / env 覆盖 / 静态 fixture JSON）→ 不上图。
- **复发频率**：跨任务反复要才上，一次性的留 task-local（核心页面的关键状态首次见到即可上）。

> 档位：可本地 mock 且无外部进程 🟢 / 须启动 mock server 或配置测试环境 🟡 / 真实第三方调用·真实用户数据 🔴。

## 只存地图，不存细节，不存实体

- **地图**（本手册）：有哪些料 / 作用 / 档 / 起手坐标。稳定低腐。
- **细节**（完整 mock JSON / fixture 内容）：易腐，用时翻代码。
- **实体**（测试账号密码、临时 token）：volatile，当次造。

每条只四样：**名 · 作用（哪些 case 要） · 档 · 起手坐标**。

起手坐标写法：`MSW handler 路径` / `mock server 启动方式` / `第三方沙箱地址` / `测试账号申请渠道`——要具体到拿着就能操作。🔴 料只标"别自助、直接摊牌"。

料少合一份 `物料地图.md`；某域读着累了再拆 `物料地图-<域>.md`。

## 扫码入口

从三处入手，覆盖率最高：
1. **API 层目录**——扫 endpoint 列表，找哪些接口的 mock 需要启动 MSW / mock server
2. **test 目录**——扫已有 fixture / handler，识别已沉淀的物料
3. **CI / docker-compose 配置**——扫测试阶段启动了哪些外部服务

## 和其他文档的边界

| 文档 | 职责 |
|------|------|
| **`test-knowledge/物料地图[-<域>].md`** | **需 setup 的测试物料：有哪些 / 作用 / 档 / 起手坐标（本手册）** |
| `delivery/<task>/test/materials.md` | 单任务物料实体台账 |
| `test-knowledge/测试物料获取指南.md` | 物料获取的三档 policy；本手册档位继承它 |
| `docs/module-knowledge/` | 业务模块领域知识；地图起手坐标指向它们 |
