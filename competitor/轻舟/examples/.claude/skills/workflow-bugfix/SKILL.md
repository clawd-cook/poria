# workflow-bugfix：缺陷定位（工作流起步节点）

本节点是 bug 类 profile 的**起步/触发节点**（profile 的 `start_node`）：跑 `/workflow-engine init` **之前**的第一步，专做「复现 + 定位根因 + 圈爆炸半径」。它**在状态机之外**——和 feature 流的 `workflow-explore` 同位，是分阶段加载的有意设计，不是例外：

- **起步只加载定位问题所需的**：`docs/spec-rule/design-rule.md`（规约必守 + 经验/踩坑段扫一遍）+ 相关 `module-/tech-knowledge` + 用户带来的问题描述（报错正文 / 告警单 / 复现步骤 / 日志片段）。
- **刻意不加载工作流编排细节**（PROTOCOL / profile / 状态机机制）：既省上下文 token，又让定位思考不被流程纪律压着。编排细节在根因谈清、人手动 `init` 之后才加载。

结论靠**同会话上下文**传给下游，不落文件。这份根因分析就是 bug 流的「设计依据」——替代了 feature 流的 TRD，故 bug 流没有 propose 节点。

## 定位（复用 trouble-shooting）

进入即**复用 `trouble-shooting` 并完整继承其 stance**：拉调用链日志、定位源码、按需查 DB/DUCC/JimDB/ES，一步步把假设用实际数据验证成结论。

**核心纪律（继承 trouble-shooting）：**

- **结论必须有数据支撑**——禁止输出「可能是 XX」的猜测；假设必须经实际数据验证后才成为结论。
- **流程自适应**——每阶段结束判断「当前信息是否已能确定根因？」，能则直接收敛，不强制线性走完所有查询。

如果找不到 `trouble-shooting` 直接退出，提示用户。

## 本节点要谈清的三件事

定位不是查到日志就完，要谈清下游 init 后需要的三样上下文：

1. **根因**——bug 到底由什么引起，落到具体源码位置 / 数据 / 配置，有数据支撑。
2. **复现路径**——什么输入 / 什么条件下必现。这是下游 test-plan 写「复现该 bug 的全链路用例」的基准，也是 run-autotest 判「修复是否真生效、是否不再复发」的 oracle 来源。
3. **爆炸半径**——这个根因还影响哪些链路 / 场景。圈定它 = 圈定回归测试范围，防止修一处塌一片。

三件事没谈清就 init，下游 test-plan / run-autotest 会失去判定基准——这是严重问题，别把它漏到后面环节。

## 边界

- **不动手改代码**：这里只定位、不修复。修复在 init 之后的 `workflow-implement` 节点做，且以「最小化改动、精准命中根因」为原则。
- **不追问打断成 QA 问卷**：能顺着数据查下去就查，需要用户给的（复现环境、权限、告警单原文）直接索要，但不要把它做成一问一答的诊断问卷。

## 出口

根因、复现路径、爆炸半径三件事谈清后，仅提示，不做动作：

> 根因已定位（附一句话根因 + 复现路径 + 影响范围）。准备好就跑 `/workflow-engine init <task> --profile bugfix` 开始修复任务。
