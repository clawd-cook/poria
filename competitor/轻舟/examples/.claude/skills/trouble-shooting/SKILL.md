# 线上问题排查 (trouble-shooting)

## 前置依赖

本 skill 依赖 `lbcli` CLI 查日志、查库、查配置、查缓存、查 ES。**所有 opencli 命令的用法、窗口/profile/环境/JSON 引号等工具纪律，一律遵循 `lbcli` skill**，本文不重复。

- 未安装时，提示用户参照安装文档：https://joyspace.jd.com/pages/kaTvveuy6Tt6tkuvIJwu

## 项目地图准备

「代码定位」「配置读取」依赖一份**项目地图**（应用名 → 仓库路径）。开始前：

1. 读取 `~/.claude/project-map.md`，存在则直接用。
2. 不存在 → 提示用户把本 skill `assets/project-map.template.md` 复制为 `~/.claude/project-map.md`，并改掉「代码根目录」为本机仓库目录，完成后再继续。

地图里的代码路径 = 「代码根目录」+「相对子路径」拼接，使用前确认根目录是当前用户的真实目录。

---

## 排查原则

1. **流程自适应**：以下阶段不强制线性执行。每阶段结束判断「当前信息是否已能确定根因？」——能则直接跳到阶段 6。

2. **结论必须有数据支撑**：禁止输出「可能是 XX」的猜测。假设必须经实际数据验证后才能成为结论。

3. **配置以线上实查为准**：代码里看到的默认值不等于线上实际值（DUCC 配置可能已被改过）。涉及配置的判断一律实查线上，不信代码默认值。

4. **查不到数据时如实说明**：穷尽合理手段仍拿不到关键数据（无权限 / 已过期 / 日志已滚动）时，输出「无法确认，缺少 XX，需要 XX 权限或人工介入」，不无限重试、不降级成猜测。

## 阶段 1：信息提取

从输入解析以下字段：

| 字段 | 提取方式 | 无法提取时 |
|---|---|---|
| 应用名 | 告警单字段 / 关键词匹配地图关键功能列 | 交互询问 |
| 时间 | 告警单时间戳 / 描述中的时间点 | 标记「无时间」|
| 错误关键词 | 异常类名、错误码、业务关键词（订单号、PIN 等） | 从描述归纳 |
| traceId | 告警单给出则直接用 | 留待日志中提取 |
| 环境 | 告警单环境字段 / 描述中的环境词 | 默认 pro |

**交互策略**：仅应用名、时间无法推断时才问用户，最多问这 2 项，其余在排查中自行发现。

**命中未知应用时**：应用名不在地图映射表中，向用户询问其「代码路径」，确认后追加一行到 `~/.claude/project-map.md`，再继续。

---

## 阶段 2：日志拉取

> 命令参数、窗口/profile 细节以 `lbcli` skill 为准。

### 时间窗口策略

```
用户给了时间 → history，精确时间前后 3 分钟
用户没给时间 → 先 live
                ├ 命中 → 用
                └ 空   → 兜底 history --hours 24
                          ├ 命中 → 用
                          └ 空   → 告知用户「最近 24h 未查到问题原因，请提供具体发生时间」，待补时间后定向查
```

- 给了时间：`logbook grep "<关键词>" --app <app> --env <env> --mode history --start-time "..." --end-time "..." -f json`
- 没给时间：`logbook grep "<关键词>" --app <app> --env <env> -f json`（默认 live）

### 两步查询

1. **业务关键词定位**：用错误码、异常类名、PIN、订单号查入口应用日志，从命中行提取 `traceId`（值通常是 `{num}.{num}.{num}` 三段式，如 `4078010.52829.17813025360063341`）。
2. **traceId 全链路查询**：用 traceId 查同一应用完整调用链路日志。

### 下游应用展开（按需）

链路日志出现 RPC / HTTP 报错时：从接口名/服务名推断下游应用 → 对比地图确认 → 用同一 traceId 查下游 → 递归到最终报错落点。

---

## 阶段 3：代码定位

从日志提取 `类名.方法名`。仓库路径 = 地图「代码根目录」+ 该应用「代码路径」：

```bash
grep -r "class XxxService" <仓库路径>/src --include="*.java" -l
# 读取报错方法上下文（±50 行）
```

- **跨应用**：按地图切换仓库路径再 grep。
- **路径不存在**：地图条目已过时，提示用户更新 `~/.claude/project-map.md` 的根目录或该应用路径，确认后再继续。
- **遇到配置读取**（`DuccConfig` / `@DuccValue` / `DuccClient.getString` 等）：提取 config key，**实查线上**，不用代码默认值（见阶段 5）。

---

## 阶段 4：形成假设

结合日志 + 代码，提出 1-2 个最可能的根因假设，每个注明：假设内容、支撑证据（日志行 / 代码行）、待验证数据（DB/DUCC/JimDB/ES）、置信度（高/中/低）。

置信度「高」且无需外部数据验证时，直接进入阶段 6。

---

## 阶段 5：数据验证（按假设按需触发）

> 命令用法以 `lbcli` skill 为准。

- **DB 查询**：先读对应应用配置文件拿数据源（查找规则见地图「配置文件读取规则」），再 `dongdal query`。表结构可在仓库下查找 `.sql` 后缀文件（见 `lbcli` skill）。
- **DUCC 配置**：`ducc getconfig`——代码有默认值时也必须实查。
- **缓存**：`deeptest jimdb`。
- **ES**：`jes query`。

每次验证后更新置信度，升至「高」即可输出，不必穷举所有验证项。

---

## 阶段 6：输出结论

```
## 根因结论
[一句话：是什么问题、在哪发生]

## 证据链
1. 日志：[关键日志行摘要，含时间/traceId]
2. 代码：[文件路径:行号] — [关键逻辑]
3. 数据：[查询结果摘要，如何支撑结论]（查了 DUCC 则注明：实际值 vs 代码默认值）

## 调用链路
[入口应用] → [中间应用] → [最终报错落点:应用名/类名/方法名]

## 修复建议
[具体到文件路径:行号的修改方向]
```

**禁止出现**「可能」「疑似」「推测」「大概率」——置信度不够就回阶段 5 继续验证，不降级输出猜测。
