## 内容生成提示词

最终三节：**项目身份**（一句话定位 + 5-10 领域术语）/ **项目地图**（页面路由·组件体系·状态管理·接口层·构建部署）/ **业务模块索引判档** / **项目特有红线 + 知识索引**。形态参照 `docs/project-overview.md`。

### 扫码（直接产出 `docs/project-overview.md`）

**工作模式**：自主分析项目事实，交付每个节段的结论。大部分业务是复杂的，建议一步一步慢慢来，保障文档质量为准。

先确认项目框架栈（React/Vue/Next.js/Umi/Vite 等），再按下表逐节填项目地图。每节 ≤ 8 行，超出二次聚合到业务域。

**常规节段**（每个项目必扫）：

| 节段 | 收什么（语义边界） | 处理 |
|------|--------------------|------|
| 目录约定 | src/ 下的分层惯例（pages/features/shared/utils 等） | 列各层目录 + 职责边界 + 命名惯例 |
| 组件体系 | 项目的组件分层（页面组件 / 业务组件 / 基础组件 / UI 库） | 列各层目录 + 识别标识 + 所用 UI 框架（Ant Design / Element 等） |
| 状态管理 | 项目全局/跨组件状态管理方案 | 列方案（Redux/Zustand/Pinia/Context 等）+ store 目录 + 3-5 个核心 store/slice |
| 接口调用层 | 项目与后端交互的 HTTP 请求层 | 列封装方案（axios/fetch/umi-request 等）+ 目录 + 鉴权方式 + mock 方案 + 拦截器惯例 + 3-5 个核心 API 模块 |
| TypeScript / 类型体系 | tsconfig 分层、shared types 目录、API 类型生成方式 | 列 tsconfig 结构 + 类型目录 + 自动生成工具（如 openapi-typescript） |
| 样式方案 | CSS 组织方式（CSS Modules / Tailwind / styled-components / Less/Sass 等） | 列方案 + 主题/设计 token 位置 + 全局样式入口 |
| 构建与工程化 | 构建工具链、monorepo 结构、环境变量管理 | 列构建工具 + 包管理器 + 环境配置文件 + monorepo 方案（如有） |
| 测试体系 | 单测 / E2E 框架与覆盖率配置 | 列框架（Jest/Vitest/Playwright/Cypress）+ 配置位置 + 覆盖率门槛（如有） |
| 部署与发布 | 部署目标与 CI/CD 流程 | 列部署平台 + 构建产物类型（SPA/SSR/SSG）+ 发布流程 |
| 第三方依赖 | 项目核心第三方库（非 UI 框架本身） | 列 3-8 个关键依赖 + 职责（图表库 / 富文本 / 地图 / 国际化等） |

**可选节段**（按项目类型按需扫，无信号跳过）：

| 节段 | 适用场景 | 处理 |
|------|----------|------|
| 页面路由 | 多页面应用（SPA/MPA） | 列路由组织方式（文件系统路由 / 配置式）+ 路由前缀分组 + 3-5 个核心页面路径 |
| 权限与路由守卫 | B 端项目 | 列鉴权模型（token 存储 / 刷新机制）+ 路由拦截层 + 权限粒度（页面级 / 按钮级） |
| 实时通信 | 有 WebSocket / SSE / 轮询需求 | 列方案 + 订阅的 topic/channel |
| 微前端 / 模块联邦 | 多团队协作 / 子应用架构 | 列框架（qiankun/Module Federation 等）+ 主子应用边界 |

**判档规则**（按用法种类数自动判，不要主观）：

| 用法种类 | 档位 | 写法 | 标识 |
|---------|------|------|------|
| 1-2 | 精确档 | 直接陈述各自适用范围 | 不打 |
| 3-5 | 混乱有规律 | 按模块 / 路径 / 职责总结规律 | 打 `_[AI 推断/待 verify]_` |
| 5+ | 无统一规律 | 声明放弃抽象、写「按需 grep」 | 打 `_[AI 推断/待 verify]_` |

**兜底**：节段无信号写「无」；package.json 中无前端框架依赖（react/vue/svelte/angular/next/nuxt 等）则退出。

**内部框架栈**：如团队有内部脚手架或统一 CLI 工具，在此注明并指向对应 `docs/tech-knowledge/` 文档；无则以 package.json 为准。

## 业务模块索引判档

（索引粒度 = 业务域，知识规模 = module-knowledge 那层吸收，两条轴分开）

指针位置给 1-3 个**切入点路径**（页面入口 / 核心 feature 目录 / 状态 store 这类「能往下挖」的锚，非全量枚举）

收口：**索引永远一行一域；给 ≤3 路径、复杂域指向 module-knowledge，让模块内部拆分，本处不处理。**

**数量**：业务模块最多 10 个，多了模块合并或删除低价值模块，少了不硬凑、如实写。

**排序**：索引按「复杂度 × 重要性」从高到低排，最值得优先沉淀文档的域在最前——这样沉淀才小投入大回报；业务本身不复杂的，沉淀反而是增加维护负担。

### 代码看不出的三件事（扫码时一并推断，打 `_[AI 推断/待 verify]_`）

从 README / 注释 / 组件名 / 路由名等线索推断，推断不出就留空、不硬凑：

1. 一句话定位：对谁、提供什么能力、解决什么场景
2. 5-10 个核心领域术语：中文 / 别名 / 一句解释
3. 项目特有红线 1 条，仅示例作用（前端典型如：禁止直接操作 DOM / 所有异步请求必须经过统一拦截器）

落盘后有问题当场追问修改，文件随时可改，不专设人审环节。

## 核心原则

- 预算不设上限，一定要把问题讲清楚。但每行都有 token 价值，能从代码推导的不重复。
- 领域术语要评估价值，没有不硬凑，价值不够需剔除。
- 「在哪 + 怎么识别 + 关键示例」，不做全量枚举。
- 诚实优于硬抽象：技术栈混乱直接讲混乱，不硬归纳。
- `_[AI 推断/待 verify]_` 只打「混乱有规律」和「无统一规律」档。
- **触发式索引（tech 那块）不归本 skill 挖**：本步只把它留成占位（`涉及xxx → tech-knowledge/xxx.md`），通用技术设计 topic 由下游 `bootstrap-tech-topic` 通读项目后回填。本 skill 别去推 tech，避免和它重复/抢写同一段。

## 和其他文档的边界

| 文档 | 职责                                                                        |
|------|---------------------------------------------------------------------------|
| **`project-overview.md`** | **始终加载的压缩包：触发索引 + 极简红线 + 项目地图**                                           |
| `spec-rule/` | 团队级通用规范                                                                   |
| `tech-knowledge/` | 本项目特有的通用技术设计机制（被 overview 触发式索引指向；索引由 `bootstrap-tech-topic` 回填，非本 skill） |
| `module-knowledge/` | 单业务模块的业务知识（AI 按业务名查找）                                                     |
