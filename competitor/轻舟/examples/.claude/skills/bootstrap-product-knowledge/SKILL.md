# bootstrap-product-knowledge：产品知识库生成

服务**产品**，不服务研发。以项目代码库为事实依据，把产品事实——能力边界、玩法、规则、术语——梳理沉淀成产品层面的知识库，作为下游「产品知识库」的输入载体，在写 PRD 阶段提供事实支撑。

> **职责边界**：本库只负责把产品事实沉淀准、沉淀全。核心动作是**蒸馏**——从代码事实里提炼出产品的「判断依据」（能力边界、关键规则、决策点全景），下文所有「蒸馏 / 重蒸馏」都指这一动作。**代码是主依据**，AI 直接分析代码即可产出主体内容；历史 PRD 仅作可选补料，没有也能正常运行。

> 与代码库里 `project-overview` / `module-knowledge` 的区分：那两个长在业务代码仓、服务研发（怎么快速理解项目、怎么写代码）；本知识库长在**独立仓库**、服务产品（产品长啥样、能力边界在哪）。物理隔离，互不覆盖；研发侧文档可作为本轮生成的**参考事实**，但结论与措辞按产品视角重写。

## 产物结构（独立仓库）

按产品名建一级目录；目录内先一篇产品汇总，再按能力域开二级目录；**能力域内部按模块拆文档，模块复杂时再二次拆分为子文档**。

```
<产品名>/
├── product-overview.md          # 产品汇总（顶层薄片，常驻）；内含能力地图（产品域全景索引）
├── capability-map.json          # 能力地图的结构化镜像（供线上系统读取）；与全景表同源，见下节
└── <能力域>/                     # 一个能力域一个二级目录
    ├── <能力域>.md               # 域概览（可选）：本域有哪些模块、各自定位、互相关系
    ├── <模块A>.md                # 模块级细化文档（粒度足够时一篇即可）
    └── <模块B>/                  # 模块复杂 → 二次拆分为子目录，每个子能力一篇
        ├── <子能力B1>.md
        └── <子能力B2>.md
```

- **拆分是常态**：默认倾向「拆细」而非「合并成一篇」——一篇大而浅的文档支撑不了写 PRD。具体拆分信号属场景 2 写作指导，见 `references/refine.md`。
- 能力地图（产品能力大地图索引）落在 `product-overview.md` 里，作为「产品域全景」段，链向各二级目录的细化文档。
- **能力域二级目录名、其主文档名，一律用该域的中文名**（与全景表、`capability-map.json` 的 `name` 完全一致，如 `用户引流/用户引流.md`）。中文名即目录名即主键，不再另起英文名。

## 能力地图结构化镜像（`capability-map.json`）

`product-overview.md` 里的「产品域全景」是给人读的表格；线上系统需要机器可读的同一份数据，落成 `<产品名>/capability-map.json`——它是全景表的**孪生镜像**，域数、中文名、职责、状态一一对应。**强约束：凡动过全景表就必须同轮同步 json，二者漂移视为未完成。** 动地图前读 `references/capability-map.md`（完整 schema、字段约定、强约束），本文其余各处只留动作提示、不复述规则。

## 输入与事实来源

每个产品目录下有两个**输入文件**（人写、机器读）：`<产品名>/codebase.json`（代码库关系表：产品目录名 + 可选中文名/描述 + repos 清单，每个 repo 含 git/role/可选 branch）与 `<产品名>/context.md`（范围、排除项、领域备注等自然语言）。**完整 JSON 结构见场景 0**——建/改这两个文件是场景 0 的活，其它场景只读不写。

代码库本身**不在本仓库**，由本 skill 自带的 `tools/codebase.py`（位于 skill 目录下）统一缓存到 `~/.product-knowledge/codebase/<org>/<repo>`（云端沙箱下 `~/workspace/<repo>`，代码由外部预置）。**不要自己拼本地路径**，一律通过该工具拿。脚本从**当前工作目录**（知识库仓库根，产品目录 + `codebase.json` 所在处）读清单，故须在仓库根运行。

**每次运行本 skill，第一步先拉最新代码**（`$SKILL_DIR` = 本 skill 的 base directory）：

```bash
python3 "$SKILL_DIR/tools/codebase.py" clone <产品名>     # 不存在则 clone、存在则 pull，并 checkout 指定分支；失败不阻断
python3 "$SKILL_DIR/tools/codebase.py" list  <产品名>     # 输出 [{git, role, branch, path}, ...]，从 path 读代码
python3 "$SKILL_DIR/tools/codebase.py" path  <git链接>    # 运行期单个 repo 问路，打印本地绝对路径
python3 "$SKILL_DIR/tools/codebase.py" mark  <产品名>     # 蒸馏完一轮后调用，把各 repo 当前 SHA 记为增量基准
python3 "$SKILL_DIR/tools/codebase.py" diff  <产品名>     # 增量更新时调用，对比基准 SHA 与当前 HEAD，输出各 repo 变更文件清单
```

**增量更新基准**：`<产品名>/.knowledge-state.json` 记录「上次蒸馏时各 repo 的 commit SHA」，是增量更新的唯一基准。**每次成篇蒸馏（冷启出汇总、细化出文档、增量刷新文档）后，都要 `mark` 一次**，把基准推进到最新；否则下次 `diff` 会把已经蒸馏过的改动重新算成「待更新」。

知识库的全部内容都以事实为依据，事实来源是公共的：

- **多个项目代码库（主依据）**（路径由上面的工具给出）——含其 `project-overview` / `module-knowledge` 作参考（研发视角，需按产品视角重写结论）。AI 直接分析代码即可产出主体内容。
- **`context.md` 用户补充**——初始化输入：范围、排除项、领域备注。
- **产品历史 PRD 文档（可选补料）**——有则锦上添花，没有也能正常运行；注意 PRD 可能含过时内容，与代码现状冲突时以代码为准。

场景 1 全量扫、聚类成域；场景 2/3 聚焦到目标能力域相关的那部分，不必每次重扫全量。

## 场景判别（进来先判，无人传场景）

上游点名调用、**不传场景也不传诉求**。进来后按下表自判，再走对应动作。「用户诉求」一律从**当前对话上下文**读取（调起本 skill 的环境里若带了诉求就用它；没有则只能走场景 1 的全量生成）。

| 判别条件 | 场景 | 动作 |
|---|---|---|
| 上下文带「建库/加代码库/改分支/改职责描述」等配置类诉求，或 `<产品名>/codebase.json` 尚不存在 | **0 配置** | 建立或修正输入文件（`codebase.json` / `context.md`），不产出知识内容 |
| `<产品名>/product-overview.md` 不存在（有输入文件、无产品地图） | **1 冷启** | 全量生成：产品汇总 + 能力地图 |
| 已有汇总+地图，且上下文带「细化某能力域」诉求 | **2 细化** | 按诉求生成对应能力域的细化文档 |
| 已有汇总+地图，且上下文带「修正/补充」知识内容的诉求 | **3 修订** | 定位目标文档，做适当修正或补内容 |
| 已有产出，且上下文带「代码更新了/同步最新/增量更新」诉求 | **4 增量** | diff 出变更代码，只刷新已生成的受影响文档；待细化域跳过，全新域仅提议 |

判不出场景（有地图但上下文无任何诉求）→ 停下来说明现状、请上游给出细化/修订诉求，不臆造。

**场景 0（配置）与场景 3（修订）的分界**：场景 0 动的是**输入文件**（`codebase.json` 的产品名/中文名/描述/repo 清单/分支、`context.md` 的范围与背景）；场景 3 动的是**已产出的知识文档**（汇总或域细化）。改代码库来源走 0，改梳理结论走 3。

## 各场景动作步骤

### 场景 0 配置

管理**输入文件**（`codebase.json` / `context.md`）的建立与修正，不产出任何知识内容。两种子情况共用一套动作：初次建库（无 `codebase.json`）、已有库改代码库来源（加/删 repo、改分支、改职责描述、改产品中文名/描述、调范围）。

1. 从对话上下文收集信息：产品目录名、中文名、一句话描述、各 repo 的 git 链接 + 职责 + 分支（不填即默认分支）、范围与排除、领域背景。**AI 猜不出代码库清单和 git 链接，缺就问，不臆造。**
2. 落 `<产品名>/codebase.json` 与 `<产品名>/context.md`。修正场景只动相关字段，不重写无关部分。`codebase.json` 结构：
    ```json
    {
      "product": "产品目录名（英文 kebab-case，与目录同名）",
      "name": "产品中文名（可选，仅人读元信息）",
      "description": "产品一句话描述（可选，仅人读元信息）",
      "repos": [
        { "git": "git@host:org/repo.git", "role": "职责说明", "branch": "分支名（可选）" }
      ]
    }
    ```
    - `name`/`description` 是**仅人读元信息**：标识产品是啥；AI 生成汇总时可参考，但不强依赖（结论仍以代码事实为准）。
    - `repos[].branch` **可选**：某代码库要蒸馏的不是默认分支时填它；不填则用远端默认分支。分支为**全局单缓存**——同一 repo 只有一份目录，`clone` 时 checkout 到指定分支。
    - `context.md` 是自然语言补充：范围、排除项、领域备注。
3. **初次建库务必先停**：把生成的输入文件给用户确认无误后，才可进入场景 1 冷启。改分支/改 repo 后建议提示用户重跑一次 `clone` 以对齐本地缓存。

### 场景 1 冷启

1. **全量扫事实**：先 `clone` 拉最新代码，再 `list` 拿各 repo 本地路径，结合 `context.md`，按「输入与事实来源」扫齐当前产品的所有上下文。
2. **聚类成域**：把能力按产品域聚类，定出有哪些域、各域一句话职责。
3. **决策点探测（聚类之外的第二遍扫描，必做）**：业务决策点它们看着人畜无害，全景却散在各处，是本库最难重建、最该沉淀的模块。冷启不是扫代码文件夹名，而是要找「硬逻辑在哪」。所以聚类完再过一遍全量，凡命中「决策点怎么写」里那四条信号的模块（① 同输入不同结果的千人千面；② 多候选竞争同一结果；③ 候选间有优先级 / 互斥 / 覆盖；④ 代码里有明显的圈选规则 + 优先级排序 + 兜底默认值）就**登记下来**。判据别停在目录名：`grep` 枚举 / 分发器 / 策略工厂 / 优先级排序 / 兜底默认值这类信号，定位到「多候选竞争出唯一结果」的真实热点。**此步只探测 + 定位 + 计数，不展开候选全景**（全景是模块级、属场景 2）。
4. **落产品汇总** `product-overview.md`（顶层薄片，结论落这）：
    - 一句话定位：对谁、提供什么核心价值、解决什么场景。
    - 核心领域术语：产品级、跨域通用的黑话；价值不够不硬凑。
    - 产品域全景（= 能力地图）：有哪些域、各域一句话职责、各域细化文档的链接。**并在对应域上标出决策点信号**——命中第 3 步探测的域，注明「本域含 N 个决策点候选，待细化」之类标记，让地图携带复杂度信号、别让所有域看起来一样平。这既是冷启最便宜的插旗时机，也为后续细化定优先级。此步只产汇总 + 地图骨架，**不展开**每个域的细化与候选全景（细化交场景 2 按需做）。
5. **同步落 `capability-map.json`**（schema 见 `references/capability-map.md`）：把全景表里每个域写成一条。冷启阶段各域都还没细化，`status` 一律 `planned`、`doc` 为 `null`，`name` 用该域的中文名（即将来建目录时的目录名）。域集合、中文名、职责须与全景表逐条对齐。
6. **收尾 `mark`**：`mark <产品名>` 把各 repo 当前 SHA 记为增量基准，供日后场景 4 增量更新对比。

### 场景 2 细化
按诉求锁定目标能力域，深挖相关代码 + PRD，按需拆篇生成/更新细化文档，回填能力地图与 `capability-map.json`，收尾做忠实度校验并 `mark`。

**动手前必须完整读 `$SKILL_DIR/references/refine.md`**——「写判断依据不写查得到的事实」「决策点候选全景怎么写」「独立忠实度校验」等本库最核心、最易做浅的写作判据全在那里，是本场景的完整步骤，不可凭印象跳过。

### 场景 3 修订
生成后的**人工纠偏入口**：用户看完产出，指出某块梳理得不准、或补充一段历史背景/经验时，走本场景。
1. 按诉求定位目标文档（汇总或某域细化文档）。
2. 做最小必要的修正/补充，不顺手重写无关段落。若用户补的是设计背景/历史经验，按 `references/refine.md` 的方式**编织进对应事实旁**。
3. 若动到了域的增删或链接，同步更新 `product-overview.md` 的能力地图**及 `capability-map.json`**（两者一致）。若用户修正的是某域中文名或职责，也同步改这两处对应字段。

### 场景 4 增量更新
代码更新后把变动同步进**已经生成的**文档。核心三步：**diff 代码 → 对代码锚点判断哪些已有文档受影响 → 按场景 2 写法重蒸馏覆盖**，收尾 `mark`。**一条铁律：增量只更新已生成的文档，绝不新建域或文档**——待细化域跳过，真·全新域只提议、由用户拍板。

**动手前必须完整读 `$SKILL_DIR/references/incremental.md`**——`diff`/无基准退化/锚点比对/铁律的完整步骤全在那里，重蒸馏写法复用 `references/refine.md`。

## 收尾
涉及域/文档增删的，确认 `product-overview.md` 的能力地图索引已同步。
**凡本轮动过全景表**，按 `references/capability-map.md` 的收尾校验逐条核对 json 与全景表一致。
产出/更新了知识文档的（冷启、细化、增量），确认已 `mark`，把增量基准推进到本轮蒸馏的 SHA。
