# 场景 2 细化：完整写法

> 本文件是 `SKILL.md` 场景 2 的按需加载详解。**细化某能力域动手前必须完整读本文**——本库最核心、最易做浅的写作判据全在这里。场景 4 增量重蒸馏时的「写法」与「忠实度校验」也复用本文。

1. 按诉求锁定目标能力域，回「输入与事实来源」挖该域相关的代码库 + PRD 细节（必要时 `clone` 更新、`path`/`list` 取路径）。
2. **先判拆分，再动笔**：按下面的拆分信号，定出这个域要拆成几篇（域概览 + 各模块，复杂模块再拆子能力），列出文档清单。默认倾向拆细——别一上来就奔着一篇写。调研阶段就按这个清单分头深挖，不要给每个能力只挖一段概览级素材（素材的深度决定文档的深度）。**深挖 = 读完整的核心类、相关实体/枚举、定时任务等，把一条业务规则的来龙去脉读全；只读片段拿个概览，写出来必然浅。**

    **拆分是常态，不是例外**。默认倾向「拆细」而非「合并成一篇」——一篇大而浅的文档支撑不了写 PRD。判断信号，命中任意一条就拆：
    - 模块下有多个并列子能力 → 每个子能力一篇。
    - 单个能力的配置项 / 状态 / 边界场景多到一篇写不透（写满仍嫌挤）→ 独立成篇。
    - 某子能力的业务规则深挖后自成体系（产品模型 + 多条关键规则 + 现状行为）→ 从总览里**抽出来独立成篇**，总览只留一句话 + 链接，别把深度内容压回总览。
    - 同一能力的 B 端配置与 C 端落地都需要展开 → 可分篇或分大节。

    宁可多开几篇短而透的，也不要压成一篇长而浅的。拆分后在域概览或上级文档里留索引串起来。**能力域二级目录名、其主文档名一律用该域中文名**（与全景表、`capability-map.json` 的 `name` 完全一致，如 `用户引流（获客）/用户引流（获客）.md`）；域内更深一层的模块子文档可继续用英文，无强制。
3. 在 `<产品名>/<能力域>/` 下逐篇生成/更新细化文档。**核心取舍——写「判断依据」，不写「查得到的事实」**：

    知识库要外化的，是老手在需求评审现场脑子里装着的那个**大方向**——那种「对它有感觉、但具体字段记不住」的判断力。它最贵、最难重建。代码细节（字段名、表名、精确默认值）最便宜，翻代码就有，记错也无所谓——这类不写，挂个索引能链到代码即可。

    **一句判断标准**：这个信息如果不知道，产品写 PRD 时**会不会做出错误的设计判断**？
    - 会 → 写进来（它是判断依据）。
    - 不会、只是用时查一下 → 不写（它是查得到的细节）。

    **别因为怕长而写浅——内容正确情况下篇幅不设上限**。模块文档没有字数天花板，只要每一句都是「判断依据」、且忠于代码事实，就尽管把一条业务规则的来龙去脉写全、把候选全景穷举透，不要为了「显得精简」而砍深度、把该展开的规则压成一句带过。唯一的闸门是**正确 + 该写**（是判断依据、不是查得到的细节），不是长度：宁可长而全，不可短而漏。注意这跟「拆细」不冲突——拆细管的是**组织粒度**（一篇只讲一件事），不设上限管的是**单篇深度**（这件事讲到透）；两者合起来就是「多篇各自短而透、但每篇都不因怕长而留浅」。当然，"不限篇幅"不等于灌水：与判断无关的实现细节、重复的铺陈、凑数的话，一句都不该有。

    **别把「业务规则」误砍成「实现细节」**：两者长得像，但判断线是「这是业务逻辑，还是代码写法」。「满群阈值默认 180、低于 200 留缓冲提前切群」「分配不是轮询，而是按建群时间取前 10% 候选池里随机选，意图是老群优先填满又防并发冲爆」「新群建好后有 1~5 分钟初始化校验期、其间不可分配」——这些是**业务规则与现状行为**，该写透；而具体字段名、表结构、精确的代码分支写法，才是挂索引即可的实现细节。怀疑自己写浅了，就问：评审现场有人追问这条规则，看文档够不够答、还是得翻代码？得翻代码 = 写浅了。

    属于「判断依据」、该写的大方向，通常是这几类（有则写、确无则跳过，别硬凑）：
    - **为什么存在**：这个能力解决什么业务问题。
    - **产品形状**：核心概念，以及概念之间的关系（产品模型）。
    - **能力边界与形态**：能做/不能做什么；有几种路径、各自区别。
    - **有业务后果的关键规则**：不知道就会把 PRD 写错的规则（含系统的现状行为，如「池子耗尽时静默失败、不告警」——陈述事实即可）。
    - **可配置的维度**：有哪些配置维度、哪些配置背后有业务含义——不是穷举字段名和校验规则。
    - **C 端流程**（若有消费者侧）：用户从入口到完成的关键步骤与分支。
    - **跨域联动**：与其他能力域的衔接点。
    - **决策点的候选全景**（若模块是「多候选竞争、靠规则裁决出唯一结果」的决策点）：把这个决策点能出现的候选**穷举成一张可扫的全景表**——这是产品最高频的查询，也最难重建。详见下方「决策点怎么写」。

    **决策点怎么写**（一类高频、易漏、最该"缓存"的模块）：有些模块表面是「一块简单内容 / 一个不起眼的取值」，实际是**一个决策点**——多个候选来竞争，靠一套「圈选 → 竞争 → 优先级 → 兜底」的规则裁决出**唯一结果**，同样的输入换个人/对象/场景，结果就不同。一个**取值**（最终按哪个价、哪张券生效、命中哪条规则）、一个**动作**（发哪条消息、走哪个策略、分配给谁）、一份**生效配置**（多条配置叠加时哪条赢）。判断线是「多候选竞争 → 单一结果」。

    - **先认出它**。命中这几条就是决策点：① 同一决策点对不同输入产出不同结果（类似 千人千面 / 千品千面）；② 有多个候选来竞争同一个结果；③ 候选之间存在优先级 / 互斥 / 覆盖关系；④ 代码里有明显的圈选规则、优先级排序、兜底默认值。这类逻辑往往看着人畜无害，全景却散在多个枚举/分发器/配置里，没人脑子里装着完整清单——**最难重建，因而最该沉淀**。
    - **落到模块级文档，一个决策点一篇**。全景很大、域也大，但域会拆到模块这个"刚刚好"的粒度；一个决策点通常正好对应一个模块。
    - **主体是「候选全景」，不是「裁决机制」**。产品的高频查询是「这个决策点能产出哪些结果 / 有哪些候选在抢」（想加新玩法先确认存量、评审被问"这里还能出什么"）——这是热路径，占文档主体：把候选**穷举成一张可扫的表**，每条一句话「是什么 / 什么时候命中」。「谁压过谁」的优先级裁决是冷路径（只在专门改裁决逻辑时才查），**降级成全景表上的一列标注**（有竞争关系的候选才标一笔），不要单开大节把裁决机制写成主角。
    - **兜底单独交代**：这个决策点什么候选都不命中时产出什么（默认结果 / 空 / 不产出），以及命中为空时的现状行为——陈述事实即可。
    - **候选和输入维度一律从当前产品代码里提取**，不要套任何预设模板（没有固定的"人/货/场"三件套——SaaS 可能是角色/租户/套餐，内容产品可能是用户/内容/时段）。骨架（决策点/输入/候选/竞争/兜底）通用，答案永远长在具体产品上。

    **职责红线——只沉淀事实，不做评审**：本库写「现状是什么」，到此为止。**严禁**罗列「待产品明确的决策点」「研发会追问什么」「这里该怎么定义」之类清单——哪怕只陈述不替产品拍板，那也是下游产品评审 skill 拿本库当输入去挖的活，不是知识库的职责。事实与「待决策项」之间的分界，就是本库与评审 skill 的分界。唯一例外是 `待产品侧确认`（仅用于「我对这条事实本身吃不准、需要人确认」，不是「这个事实引出的产品决策」）。

    **设计意图与演变**（为什么这么设计、怎么演变到今天）：有据可循时（PRD 或人工补充的背景/经验），**编织进对应事实旁边**，让事实「活」起来；用自然语言区分事实与意图（「代码现状是…」「当初这么设计是为了…」）。无据则只讲代码事实，**不留「待补充」占位坑**——意图是锦上添花，不是必填项。

    拿不准的事实标「待产品侧确认」，不臆造。
4. **每篇细化文档底部挂「代码锚点」**：列回查代码的稳定入口——后端 service/实体类名 + 模块路径、前端菜单路由名、接口前缀、关键配置项 key。**只挂稳定入口，不挂行号**（行号随迭代漂移、导航价值低还误导；定位到类后翻实现是举手之劳）。锚点是「判断依据」与「查得到的细节」之间的桥：文档讲大方向，要精确实现就顺锚点回代码。
5. 写完回 `product-overview.md` 的能力地图，把该域的细化文档（多篇则挂域概览或主文档）挂上链接。**同步更新 `capability-map.json`**：把本域那条从 `status: planned` 改为 `generated`、`doc` 填上刚挂的中文文档相对路径（`name` 不变，目录即照 `name` 建）。若本轮新拆出了全景表里原先没有的域，json 也补上对应条目。
6. **独立忠实度校验（成文后必做，不可自己跳过）**：把素材综合成文这一步**必然丢信息、变形信息**——会把两条规则捏成一条、会把有后果的约束降级成一句带过、会漏掉素材里出现过的事实。靠「写的时候记得全面」堵不住，因为下一次的失真不会长得像你记住的任何一条。所以收尾前要拿**产出物去对素材**，而不是凭印象自检。
    - **谁来做**：派一个**没参与写作**的校验 agent。写的人带着「想这么归纳」的执念，自己查不出自己的捏合与降级；换一方只做核对，才暴露得出来。
    - **怎么核对**：把本轮调研素材（各调研 agent 的结构化笔记）和已落地的细化文档一起给它，逐条比对——**素材里每一条「有业务后果的规则 / 跨模块约束 / 现状行为」，文档里是否都还在、且没被合并稀释、没被降级成顺带一提、没被说变味**。它只看「素材有、文档有没有忠实保留」，不预设会怎么错，所以能一并兜住捏合、丢失、降级、走样。
    - **判据**：对每条规则问 skill 既有的那把尺子——「评审现场有人追问这条，看文档够不够答」。半句话答不出「是什么 / 何时触发 / 什么后果 / 怎么应对」的，就是被写浅了，退回补写。
    - 校验查出的缺口，按本文的写法补回对应文档；补完再核对一轮，直到素材里的判断依据在文档里无遗漏、无降级。
7. **收尾 `mark`**：本轮细化落地后，`mark <产品名>` 把基准推进到当前 HEAD，供日后场景 4 增量更新对比。
