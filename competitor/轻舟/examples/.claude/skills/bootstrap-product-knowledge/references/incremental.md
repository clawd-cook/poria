# 场景 4 增量更新：完整步骤

> 本文件是 `SKILL.md` 场景 4 的按需加载详解。**增量同步动手前必须完整读本文**。重蒸馏时的「写法」与「忠实度校验」复用 `references/refine.md`。

代码更新后，把变动同步进**已经生成的**知识文档。核心就三步：**diff 代码 → 判断哪些已有文档受影响 → 重蒸馏覆盖**。

**一条铁律：增量只更新「已生成的文档」，绝不新建域或文档。** 变更命中一篇**已有文档所属的能力范围**（含这篇里此前没写过的新规则）→ 并进这篇一起刷新（第 4 步）；命中一个**地图已列、还没细化的域** → **跳过，不替用户补建**（它本就等按需细化，不归增量管）；变更**对不上地图上任何东西**、又确是一块较复杂的新能力域 → **只提议、不动手**（第 5 步）。

1. `clone` 拉最新代码（会 checkout 到各 repo 指定分支并对齐远端）。
2. `diff <产品名>` 拿变更清单：它对比 `.knowledge-state.json` 里「上次蒸馏的 SHA」与当前 HEAD，输出每个 repo 的变更文件列表。
    - 若报「没有增量基准」→ 说明这产品还没 `mark` 过（老库首次用增量）。此时无从 diff，退化为：让用户指定要刷新的域，或按场景 2 逐域重蒸馏；蒸馏后补一次 `mark` 建立基准。
    - 若某 repo 报「diff 失败（基准 SHA 已不在历史里）」→ 多因分支被 rebase/强推或基准提交被删。对该 repo 视为「无法增量、需人工确认范围」，别硬猜。
3. **判断受影响的已有文档**：把变更文件清单，对着**已生成文档**底部的**代码锚点**（service/实体类名、路由、接口前缀、配置 key）比对，定位哪些文档的事实可能变了。变更文件命不中任何已生成文档的锚点、或只是无关实现细节（重构、日志、格式）→ 不影响知识层，跳过。
4. **重蒸馏覆盖**：对判定受影响的**已有文档**，按 `references/refine.md` 的写法深挖变更后的代码、重写覆盖对应文档（不是打补丁式地改一两句——要重新把这条业务规则的来龙去脉读全）。只动受影响的文档，不顺手重写无关文档。**老域延伸也在这步写**——变更命中某篇已有文档所属的能力范围（哪怕是这篇里此前没写过的新规则/新配置），就并进这篇一起刷新，因为它是这篇文档该讲的事实的延伸。**待细化域（地图已列、还没生成文档）一律跳过，不因为它的代码变了就替用户提前建文档。** 若刷新过程改动了某域的职责表述，同步改 `product-overview.md` 全景表与 `capability-map.json` 对应条目（增量不新建域，故一般只可能改 `responsibility`，不改域集合与 `status`）。
5. **真·全新域只提议、不新建**：只有当变更**对不上地图上任何东西**（不命中任何已有文档、也不属于任何已列的待细化域），且确是一块较复杂的新能力域时，才在收尾向用户**报告**：「代码里新增了 X 这块能力，地图上还没有，建议新开一个能力域细化，是否要建?」——由用户拍板。增量自身**绝不**自动新建域或文档，也不擅自往能力地图里加条目。（注意区分：落在某篇已有文档能力范围内的新内容不属于这一步，它在第 4 步随该文档一起刷新。）
6. 重蒸馏涉及的文档若较多，按 `references/refine.md` 步骤 6 做**独立忠实度校验**。
7. **收尾必做 `mark`**：把基准推进到当前 HEAD，否则下次 `diff` 会重复报同样的变更。
