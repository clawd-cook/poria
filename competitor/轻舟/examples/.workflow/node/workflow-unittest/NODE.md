# workflow-unittest：逻辑自验闸门

预读 `code-rule.md` + `test-rule.md`（规约必守 + 经验/踩坑段扫一遍）。

但进入后是否真有活，取决于下面两半各自的条件，两半都空则整体空跑、直接 advance。

## 两件互不影响的事

进入后独立判两半，各干各的，不相互依赖：

### 一、全局单测（项目配置 `unittest` 字段）

整个任务的代码要不要单测覆盖——这是**项目级团队约定**，读 `.workflow/config.json` 顶层 `unittest` 字段决定。

- **`unittest: true`**：为本任务核心业务代码生成单测，本地跑通。
- **`unittest: false` 或缺省**（默认）：不生成全局单测，这半空跑。

### 二、降级单测（test-plan 标记驱动，与上面开关无关）

读 `materials` 角色区域，挑出 test-plan 阶段标了「覆盖载体=降级单测」的 plan-N（物料拿不到、e2e 跑不了，降级成单测兜底）。逐条：

- 为该 plan-N 写单测、mock 掉拿不到物料的那部分依赖、本地跑通。
- **显式记录覆盖差值**：降级单测验的是逻辑分支，不是原 e2e oracle 的端到端业务结果。在 `materials` 角色区域对应 plan-N 补一行「降级后实际验了什么 / 相比原 oracle 损失了什么」——不许把这条悄悄当成「已覆盖」，那是假绿。

没有任何降级 plan-N → 这半空跑。

## 写单测的技术栈标准

真要写单测时：如果项目已有单测，就参考项目的，如果没有就走JUnit 5规范。

## 失败处理

单测挂了（断言不过 / 编译不过）= 上游代码逻辑有错或测试本身写错——它是**闸门，不是判断**：不算 feedback、不沉淀踩坑（机器问题不是认知问题），不调 advance、state 停在本节点，提示用户回 implement 修后重跑本节点。

如果被非本次改动的既有失败拦截，可询问用户意见，同意则临时跳过。

## 出口

两半都处理完（生成的单测全绿，或两半都无活）后 `advance <task> --step workflow-unittest`，照 CLI 打印的闸门指令当场接续（指令是给你执行的，不是转述给用户手敲的）。下一步即 code-review。

产物：单测代码（散在各 module 的测试目录）；降级单测在 `materials` 角色区域留覆盖差值记录。
