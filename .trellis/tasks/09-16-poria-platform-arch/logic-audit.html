Finding Ledger

F-01 Recovery 代码使用已废弃的 eventStore API high confirmed contradiction

Design §15 F-06 明确废弃 eventStore.appendTx() 和 store.saveStage()，要求全部写入通过 saveStageTx() 单一路径。但 §4.2 Recovery 模块未同步：

冲突定位
S2 §4.2:391 this.eventStore.append(pipeline.id, [WorktreeCleanedEvent(...)]) — 使用已废弃 API
S2 §4.2:398 this.store.saveStage(interrupted) — 使用非事务方法
S2 §15 F-06 "删除 eventStore.appendTx()，统一使用 store.saveStageTx()" — 废弃声明

后果：Recovery 写入不在事务内，若进程在 saveStage 和 append 之间崩溃，事件日志与 Stage 状态不一致。后续事件回放将丢失 WorktreeCleanedEvent，导致回放重建的状态与实际不符。

最小修复

将 §4.2 的 eventStore.append() + store.saveStage() 替换为单次 store.saveStageTx(interrupted, pipeline, [WorktreeCleanedEvent(...)])。无副作用——saveStageTx 的 stage 参数已支持非 null。

F-02 GateEngine.evaluate() 签名与调用不一致 high confirmed contradiction

§14 F3 引入 gatePhase 字段区分阶段出口门禁和 deploy 门禁，§4.1 Executor 传入 phase 字符串过滤——但 §5 的 GateEngine 定义从未更新：

签名定义
S2 §5:506 static evaluate(deployResult: DeployResult, rules: GateRule[]): GateEvaluation — 2 参数
调用现场（3 参数）
S2 §4.1:239 GateEngine.evaluate(result, pipeline.config.gates, "stage_exit")
S2 §4.1:263 GateEngine.evaluate(result, pipeline.config.gates, "deploy")

后果：TypeScript 编译期即报错。更隐蔽的是——即使手动绕过，当前 evaluate 实现不按 gatePhase 过滤，所有门禁在每个调用点全部执行，CR 阶段会误跑 ci_build / merge_conflict 等 deploy-only 门禁。

最小修复

更新 §5 签名为 evaluate(result, rules, phase: "stage_exit" | "deploy")，内部 rules.filter(r => r.gatePhase === phase)。同步更新 §14 F3 中的 DEFAULT_GATES 声明以确保每条规则有 gatePhase。

F-03 Deploy 完成状态矛盾：A8 说 BLOCKED，F1 说 WAITING_MERGE high confirmed contradiction

Design v4.2 头部声称"回溯合并所有补丁到源头 sections，消除 L-01~L-08 内部矛盾"。但同一场景——deploy 完成后等待人工合并 MR——在两处给出不同状态：

矛盾 A
S2 §13 A8:1399 "Pipeline 进入 BLOCKED 状态，等待 reviewer 手动 approve + merge"
矛盾 B（修正版，权威更高）
S2 §14 F1:1552 deploy 完成后 pipeline.status = "waiting_merge"，释放 Worker
S2 §14 F1 状态机 RUNNING → WAITING_MERGE (deploy MR created)

F1 是后续终审修正且含完整状态机，应为权威。但 A8 是实施者首先阅读的"分支保护与 MR 审批"章节，保留 BLOCKED 会导致实现偏差。

最小修复

将 §13 A8 第 9 步改为"Pipeline 进入 WAITING_MERGE 状态，释放 Worker（不阻塞队列）"。删除"进入 BLOCKED 状态"措辞。保留其余 A8 内容不变。

F-04 trdScope 生产路径未定义——OutputGuard 依赖空链 high probable missing chain

OutputGuard 是安全需求 R7 的核心执行者，但它依赖的 trdScope（允许修改的文件路径模式）没有生产者：

消费端
S2 §4.1:320 guard.check(result, pipeline.config.trdScope)
S2 §6.1:567 allowedPaths: string[] — TRD 定义的目标文件路径模式
声称的生产端（仅注释，无实现）
S2 §7:713 SQL 注释 "trdScope: design stage 从 TRD.md 提取的允许修改文件路径模式，由 skill:gen-trd 产出，写入 config.trdScope"

无任何位置描述 gen-trd skill 如何从 TRD.md 提取文件路径模式、其格式（glob? regex?）、提取失败时的处理。若 trdScope 为空或未写入，OutputGuard 的 allowedPaths.some(p => minimatch(file, p)) 对所有文件返回 false——全部变更被判为 out_of_scope，Pipeline 必定失败。

最小修复

在 Design 的 gen-trd skill 或 design stage 描述中补充：(1) TRD.md 中如何声明 scope（建议 frontmatter 的 files: 字段，glob 语法）；(2) gen-trd 提取逻辑并写入 pipeline.config.trdScope；(3) trdScope 为空时的 fallback（block all 还是 allow all + warn）。

F-05 security_scan 门禁无数据源——评估永远无输入 high confirmed missing chain

security_scan 被注册为 deploy 阶段门禁，但安全扫描在 CR 阶段执行，deploy 阶段的结果对象中不含扫描数据：

门禁注册
S2 §14 F3 { id: "security_scan", gatePhase: "deploy", onFail: "block" }
扫描执行者
S2 §3:153 "security-scan/ — 不是独立 Stage，由 code-review 内部调用"
Deploy skill 产出
S2 §15 F-02:1939 { mrUrl, mrIid, repo } — 无安全扫描字段

GateEngine.evaluate 在 deploy 阶段收到的 result 来自 deploy skill（build → push → createMr），不含安全扫描结果。该门禁要么始终 pass（无数据默认通过）要么始终 fail（无数据默认不通过），两者都违反 PRD R3 "无高危/严重漏洞"的要求。

最小修复（二选一）

方案 A：将 security_scan 改为 gatePhase: "stage_exit"，在 CR 阶段出口检查扫描结果（CR skill 已调用 security-scan，结果在 CR output 中）。
方案 B：保持 deploy 门禁，但在 deploy 门禁评估时从 CR stage output 读取缓存的扫描结果（需修改 evaluate 入参为 pipeline 或 stageOutputs map）。方案 A 更简单，建议采用。

F-06 单仓/多仓 deploy 产出不同 output shape medium confirmed inconsistency

deploy stage 通过两条路径执行，产出不同的输出结构：

单仓路径
S2 §4.1:313 executeSingleRepo → deploy skill → { mrUrl: string }（单值）
多仓路径
S2 §15 F-02:1946 mergeRepoOutputs → { mrUrls: string[] }（数组）

§14 F1 的 pollMergeRequests 用 deployOutput?.mrUrls ?? [deployOutput?.mrUrl].filter(Boolean) 做降级处理，但这是 runtime 补丁而非类型契约。Stage output 的类型无法统一定义，下游消费者必须同时处理两种 shape。

最小修复

统一 deploy stage output 为 { mrUrls: string[], perRepo: PerRepoResult[] }。单仓时 mrUrls 为单元素数组。executeSingleRepo 完成后做 shape 归一化。删除 pollMergeRequests 中的 fallback 分支。

F-07 PRD 要求双角色通知，Design 只通知单角色 medium confirmed requirement weakening
PRD（权威）

F-08 Agent 空闲超时 setInterval 无清理 medium probable resource leak
定位
S2 §14 F-08:2057 const idleChecker = setInterval(() => { ... }, 30_000); — 创建定时器
无对应 clearInterval(idleChecker)

Agent 正常完成后 for-await 循环退出，但 idleChecker 继续运行。下次 dispatch 调用会创建第二个 interval。多次 dispatch 后多个 interval 并行检查各自过期的 lastMessageAt，可能 abort 不相关的 controller。

最小修复

在 dispatch() 的 finally 块（已有 clearTimeout(timer)）追加 clearInterval(idleChecker)。

F-09 handleStageError 未定义——异常路由不可达 medium confirmed missing chain
引用
S2 §4.1:291 await this.handleStageError(pipeline, stage, error)

该方法是 Executor 异常处理的唯一入口，负责将具体 Error 类型映射到 IssueClass（PRD R6 的 10 种异常场景）。Design 定义了完整的 IssueClass 枚举和 ISSUE_POLICIES，但从 Error → IssueClass 的分类逻辑和从 IssueClass → humanLoop/retry 的路由逻辑均未展开。

缺此方法，PRD R6 的全部异常处理策略无实现锚点。

最小修复

在 §4.1 PipelineExecutor 中补充 handleStageError 伪代码：error instanceof 分支 → IssueClass 分类 → ISSUE_POLICIES[issueClass] 查询 → autoRetry > 0 且 retryCount < autoRetry 则 retry，否则 humanLoop.notify()。

F-10 FAILED → CANCELLED 双重回滚风险 low probable edge case
状态机
S2 §14 F1 "FAILED → CANCELLED (manual cancel)" — 转换合法
Cancel 执行
S2 §14 F11:1899 cancel command 调用 this.rollback.execute(pipelineId)

Pipeline 进入 FAILED 时，失败处理路径可能已执行部分 rollback（如 worktree 清理）。用户随后手动 cancel 会再次执行完整 rollback 序列，尝试删除已不存在的分支或关闭已关闭的 MR。

影响有限——git 操作幂等（delete 不存在的分支报错但不损坏），但会产生 audit_log 噪声和用户可见的错误输出。

最小修复

rollback.execute 每条 command 用 try/catch 包裹，"资源已不存在"类错误记录为 info 而非 error。或：cancel command 对 FAILED pipeline 跳过 rollback，仅做状态更新 + stage 标 skipped。
